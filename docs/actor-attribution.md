# Actor possible-association

How Foiled suggests that a campaign or a lone attempt may be associated with a threat actor described in public reporting (#29), and the limits it keeps while doing so. Foiled assesses; it does not convict. A wrong definitive label is worse than silence, so every suggestion is worded "possible association", rests on cited public sources, explains every point of its score, and cannot reach `high` or leave the operator's console until an analyst confirms it.

Related: campaigns ([campaigns.md](campaigns.md), #33), the confidence layer ([confidence.md](confidence.md), #27), enrichment ([enrichment.md](enrichment.md), #11), ATT&CK mapping ([attack-mapping.md](attack-mapping.md), #26), LLM correlation ([llm-correlation.md](llm-correlation.md), #28), the console (#14), intel exports (#13), the radar and review queue (#35), the threat model and legal limits ([threat-model.md](threat-model.md), #2), and the [licence register](compliance/licence-register.md) (#38).

## Design constraints

1. **Public sources only.** Every profile rests on public documents: the pinned MITRE ATT&CK bundle, vendor reports, government advisories (for example CISA and ASD's ACSC) and MISP galaxy clusters. Each source records its URL, publisher, publication and retrieval dates, a SHA-256 pin of the document and its licence.
2. **No active collection.** Matching only compares what decoys already captured with what the sources say. Foiled never scans, probes, logs in to or otherwise touches infrastructure to learn more about a suspected actor (#2).
3. **Nexus and cluster first.** Labels prefer a nexus ("EXAMPLE-nexus loader activity") or a public cluster id (an ATT&CK group id, a vendor's temporary cluster id) over named attribution. A named group needs two independent publishers.
4. **Behaviour and indicators, never geography.** Technique overlap, indicator overlap and targeting count. Geography never counts, and a shared ASN never counts on its own.
5. **Capped in code.** Actor links go through #27 as `attempt_actor`. Whatever the weights say, a link with no shared indicator stays `low`, and no link reaches `high` or becomes publishable until an analyst confirms it.
6. **Explainable.** Every link lists the techniques (with rarity), the indicators (with the report that lists each one), the targeting, the overlaps it saw and did not count, every contribution and every cap.
7. **Deterministic.** The same captures, catalogue and decisions give the same links, ids and text.

## Sources and the pin process

### ATT&CK groups

ATT&CK groups (intrusion sets) come from the bundle pinned in [attack-mapping.md](attack-mapping.md#pinned-version), never from memory or the website. `scripts/fetch-attack.sh --groups` downloads the bundle by tag, refuses it unless its SHA-256 matches `data/attack/SHA256`, and writes `data/attack/groups.json`:

- every active intrusion set that uses, directly, at least one technique in `data/attack/techniques.json` (132 of 178 in v20.0);
- `id`, `name`, `aliases`, `stix_id` and `modified` copied unchanged; `url` is MITRE's page for the pinned major version;
- `techniques`: only the sidecar techniques the group uses, because those are the only ones a decoy can show;
- `population`: every active intrusion set, so technique rarity is measured against all of ATT&CK, not just the subset;
- `bundle_sha256`, MITRE's `notice`, `licence` and `licence_url`.

`scripts/fetch-attack.sh --check` fails if the committed file differs from what `--groups` would write. A unit test checks the file against the technique sidecar and the pinned digest. ATT&CK carries no infrastructure for groups, so an ATT&CK-only link rests on technique overlap alone and is always `low`. A version bump follows [attack-mapping.md](attack-mapping.md#update-and-review) and regenerates both sidecars.

### Curated reports

A curated profile is one YAML file under `catalogue/actors/`, reviewed in a pull request like a catalogue entry. To add one:

1. Choose a public document: a vendor report, a government advisory (CISA, ASD's ACSC, or another national CERT) or a MISP galaxy cluster at a pinned commit. Never a paid, leaked or access-controlled source.
2. Check its terms and add the publisher to the [licence register](compliance/licence-register.md#2-threat-intel-and-enrichment-sources) if it is new. Record the terms in `licence` (and `licence_url`).
3. Fetch the document once, by hand, and record `retrieved` and its SHA-256 in `sha256`. That is the pin: a reviewer can check the profile against exactly what was read.
4. Copy facts only: the technique ids the report names (each must be in the ATT&CK sidecar), indicators of infrastructure (`ip`, `cidr`, `domain`, `url`, `asn`) and tooling (`sha256`), targeted CVEs or catalogue ids, and the geography it mentions (`geo.source_countries`, recorded so a match can say it was not counted). Each indicator names its source by index. Never copy report prose.
5. Pick the label: see [Labels](#labels).
6. Run `cargo run -p foiled-lint -- .` and `cargo test -p foiled-lint --test actors`.

`foiled-core` refuses a profile with an attribution phrase in its label or notes, a named group with fewer than two publishers, a technique outside the sidecar, a missing pin, an invalid or very wide network (shorter than /8, or /32 for IPv6), or a real entry citing an example domain. Fictional entries (`example: true`) must start their label with `EXAMPLE`, say `(fictional)` in the publisher, and use only documentation addresses (RFC 5737, RFC 3849), documentation ASNs (RFC 5398) and reserved domains (RFC 2606, RFC 6761). They live only under `testdata/actors/reports/`; the API never bundles them.

Foiled ships no real curated report yet: only ATT&CK groups and the two fictional examples.

## ThreatSieve

ThreatSieve, the operator's own threat intel platform, is Foiled's single external intel hub (enrichment, #11). The actor catalogue can import from it too, on top of the bundled data:

- **What is pulled.** Actors and intrusion sets (`GET /v1/actors`), campaigns (`GET /v1/campaigns`) and reports (`GET /v1/entities?type=report`), then each actor and campaign in detail (`GET /v1/entities/:id`) for its source records, techniques, related observables and vulnerabilities. Over the `THREATSIEVE` service binding with the `THREATSIEVE_API_KEY` secret (scope `intel:read`), the same opt-in binding enrichment uses ([deploy/workers.md](deploy/workers.md#optional-threatsieve)).
- **When.** The hourly cron makes at most `calls_per_run` calls (500 by default, at most 2,000) and saves its place in the private evidence bucket, so a full sync at the default caps (about 1,500 calls) spans about four runs. This needs Workers Paid (10,000 subrequests per invocation, 15 minutes of CPU for an hourly cron); the Free plan's limits are too small. Progress is never thrown away: a 429, a 5xx, a refusal (401, 403) or an unreadable list page keeps the state and makes the same call next run, and only a sync that has made no progress for `max_sync_hours` (48) starts over. A detail that answers 404 counts as `missing`; another 4xx or an unreadable detail is skipped and listed in the snapshot's `dropped` notes (`skipped` in its counts), so one malformed entity cannot hold the sync back. A sync that finds nothing to import (nothing listed, or every detail failed) publishes nothing, keeps the current snapshot, and tries again after `refresh_after_hours`. A 408 or 425 waits like a 429. If the snapshot or pointer write fails, the next run writes both again from the saved state without calling ThreatSieve. A new sync starts once the snapshot is `refresh_after_hours` old (24). Settings: [`configs/actor-catalogue.yaml`](../configs/actor-catalogue.yaml), off by default.
- **The snapshot.** A finished sync writes `actors/threatsieve/snapshots/<synced_at>.json` and then `current.json`, a pointer with the snapshot's SHA-256. Readers refuse a snapshot whose digest differs, and serve imports only while it is younger than `stale_after_hours` (168). The digest detects a torn or corrupt write only; it is not tamper protection, because whoever can write the bucket can rewrite the pointer too. Without the binding, the key, a snapshot, or with a stale or mismatched one, the catalogue is the bundled ATT&CK groups and `catalogue/actors/` alone. API isolates read the small pointer every five minutes and read and parse the snapshot again only when its digest changed.
- **Mapping.** Each actor or campaign becomes an entry in the curated format and goes through the same checks ([curated reports](#curated-reports)): a name or alias that claims attribution drops it (aliases are dropped one by one), technique ids outside the pinned sidecar are dropped, observables must be valid indicators, and relationships ThreatSieve marks `model_inferred` are ignored. Reports that name the entity (STIX `object_refs`) become extra sources. Source titles are served with the profile, so one that claims attribution is replaced with "Report (title withheld: attribution wording)" wherever it is served, curated or imported (the curated file keeps the real title as data). Entries keep `imported` (hub, entity id, ATT&CK id, publishers, restricted).
- **Publishers.** Distinct publishers are the source records ThreatSieve keeps for the entity plus the reports naming it; a mirror of another source's record, entity or report, does not count and is not shown. With two or more, an actor may be a named group. With one, it is a cluster and every signal counts at half strength (`weight_pct: 50`, said in `not_counted`).
- **ATT&CK.** Groups (`G`) and campaigns (`C`) from ThreatSieve's MITRE source keep their ATT&CK ids (`attack:G9999`). A group the pinned sidecar already holds is left to the sidecar; ThreatSieve adds groups the pinned version does not have.
- **Pins.** ThreatSieve keeps raw source objects but gives no digest of a report document, so imported entries carry no per-document `sha256`; the pin is the snapshot digest, and each source records its retrieval date. Where a hub gives a digest it can be carried in `sha256`.
- **Licences.** ThreatSieve's entity answers carry `license` and `redistributable` per source, and `commercialUse` where the ThreatSieve version sends it. Foiled uses that flag when present; otherwise commercial use comes from a copy of ThreatSieve's licence records (MITRE, CISA KEV, MISP, IPtoASN, EPSS and NVD allow it; GreyNoise, CrowdSec, VirusTotal, ThreatFox, URLhaus and Feodo do not; anything else is unknown). An entry with any source that is not redistributable or not known to allow commercial use is `restricted`. Restricted entries stay in the snapshot but are left out of the served catalogue unless `include_restricted` is on (off by default, like `show_restricted_to_requester` in [enrichment](enrichment.md): turn it on only once your counsel has confirmed those terms allow showing them to tenants). The catalogue is global, so `include_restricted` applies to every tenant at once; there is no per-tenant setting. When served they are matched and shown with a `not_counted` note, and never exported, even confirmed.

## Labels

The display label is built by code: `ATT&CK G0000 (name as MITRE publishes it)` for groups, and `<label text> (<first publisher>)` for curated reports, so a label always says whose naming it is.

| Kind | Use it for | Example |
| --- | --- | --- |
| `nexus` | A broad origin or motive as the source states it, with no single group named | `EXAMPLE-nexus loader activity (Example Threat Research (fictional))` |
| `cluster` | A public cluster id: an ATT&CK group, a vendor's temporary or numbered cluster | `ATT&CK G0096 (APT41)`, `EXAMPLE-CLUSTER-01 (Example Threat Research (fictional))` |
| `named_group` | A named group that at least two independent publishers describe | Avoid unless the cluster id is not public |

Good: "Possible association with EXAMPLE-CLUSTER-01 (Example Threat Research (fictional)): TTP and infrastructure overlap with activity reported in ...". Not acceptable: a group number with no source, a country as the label, a label that says who is responsible.

## Matching

A **subject** is a campaign (#33) or an attempt in no listed campaign (#25). Each is compared with every profile that shares a technique or an indicator with it, found through inverted indexes, so the work is linear in the subject's techniques and indicators. Subjects read at most 2,000 indicators.

| Signal | Evidence source | How it is weighted |
| --- | --- | --- |
| Technique overlap (#26) | `actor_ttp_overlap` | Rarity per technique is `ln((N+1)/(n+1))`, with `N` every profile in the population and `n` those using the technique. Weight is `100 x (shared rarity / rarity of everything seen) x min(1, shared rarity / 5)`. One evidence item per link. |
| Observed infrastructure (#11, #33, #34) | `actor_indicator_overlap` | An indicator the defender saw in use: the attack came from it, or the decoy contacted it (IOC roles `source` and `callback`, or anything read from egress and DNS events) for a host the attacker did not name ([false flags](#false-flags)). URL 90, exact domain 85, subdomain of a listed domain 60, IP 70, IP inside a listed network 40, SHA-256 100. The only source that counts as a shared indicator. |
| Attacker-chosen values (#34) | `actor_payload_overlap` | A value the attacker chose and sent: request content, URLs in requests, payload and file hashes. Same per-type weights, but a weak source that never counts as a shared indicator ([false flags](#false-flags)). |
| Shared ASN (#11) | `actor_asn_overlap` | Weak context, never a shared indicator and never enough on its own. |
| Targeting (#12, #5) | `actor_targeting` | 100 for a shared CVE, 60 for a shared catalogue product only. |
| Geography (#11) | none | Listed in `not_counted`, never scored. |

Indicator weights are halved when the source was published more than 730 days before the subject was first seen. There is one evidence item per report indicator, at most 16, each citing the report that lists it, and each matched indicator says whether it was `observed`.

A profile becomes a link only with an indicator other than an ASN (observed or attacker-chosen), or, for technique overlap alone, with at least three shared techniques and a shared rarity of at least 5. Common techniques (`T1190`, `T1105`) therefore never link on their own. Each subject keeps the five strongest pending links plus any an analyst decided.

## Confidence and caps

Default weights (`configs/confidence.yaml`):

| Source | Points | Cap |
| --- | --- | --- |
| `actor_ttp_overlap` | 25 | 30 |
| `actor_indicator_overlap` | 30 | 40 |
| `actor_targeting` | 10 | 10 |
| `actor_payload_overlap` | 10 | 15 |
| `actor_asn_overlap` | 5 | 5 |

`foiled_core::confidence::score` then applies two caps to every `attempt_actor` link, whatever its evidence (campaign clustering, LLM or anything else included) and whatever the config says:

- **No shared indicator:** capped below `medium` (39) without `actor_indicator_overlap` evidence. Technique, targeting, ASN and attacker-chosen overlap alone is a lead, not an association.
- **No analyst:** capped below `high` (69), never `publishable` and never `auto_state_promote`.

An analyst `true_positive` sets 100, `high`, "confirmed association" and `publishable`. A link is a review queue candidate (`review_queue`) when it needs analyst attention, whatever its status: pending and at or above `radar_queue_min`, or confirmed with attempts the confirmation does not cover (`new_since_confirmation`, which includes every attempt of a confirmation recorded before covered attempts were stored). `radar_queue_min` is 40.

## False flags

Everything an attacker sends to a decoy is under their control. A false flag copies a public report: the techniques it lists, its stage-2 URL in the request, its loader's hash in the upload. Foiled therefore separates what the defender observed from what the attacker chose:

- **Observed infrastructure** is the address an attack came from, or an address or domain the decoy contacted (DNS lookups, egress) that the attacker did not name. Only it counts as a shared indicator.
- **Attacker-chosen values** count on the weak `actor_payload_overlap` source, are marked `observed: false`, and add a `not_counted` note about false flags. They are request content, URLs in requests, payload and file hashes, and callbacks the attacker directed: a DNS lookup or connection to a host named anywhere in the attempt's application, network or hook data (a JNDI lookup string, an SSRF target, a download command), and the address the decoy reached for such a host. Techniques and targeting are attacker-chosen too.

Callbacks are not proof of anything on their own. An attacker can make a decoy contact any host it names (JNDI and SSRF payloads exist for exactly this), so a callback to a host the report lists, named in the request, is a false flag as easily as it is a lead.

How the check works: for each attempt, every string in the `data` and `hook` of its application, network and hook events is normalised (percent-encoding undone twice, literal `\uXXXX` escapes decoded, fullwidth ASCII and ideographic full stops folded to ASCII, lowercased) and split into host-like tokens. A callback host is attacker-named when it equals a token or sits under a named domain (a lookup of `<data>.evil.example` after naming `evil.example`); addresses match whole tokens only, so `1.2.3.4` never matches inside `11.2.3.45`. It is decided per attempt: one attempt naming a shared host (a CDN, say) does not make it sent for another attempt that reached it unprompted. In a campaign, an indicator any member observed unprompted counts as observed.

Known ways a named host can still look observed:

- **Unicode tricks beyond the folds above:** other compatibility characters (full NFKC is not applied), confusables, and internationalised names written in Unicode in the request but looked up as punycode (`xn--...`), since IDNA is not applied.
- **Other encodings:** base64, hex, HTML entities, JSON escapes other than `\uXXXX`, string concatenation, and lookup obfuscation such as `${lower:...}` or `${::-e}` in JNDI strings.
- **Redirects:** the attacker names a host it controls, which redirects (HTTP 3xx, a CNAME or a referral) to the reported host. The second hop was never named.
- **Names hidden in dropped files:** a payload or downloaded script that carries the reported host inside a file, not in the request, so it never reaches the hook or application data.
- **Unrecorded request parts:** anything the capture did not store (bodies when payload storage is off, #16), which cannot be searched.

Whatever slips through is bounded: it can lift a link to `medium` at most, it is never publishable, and it never reaches `high` or an export without an analyst confirming it. A source address can be spoofed only for traffic that never completes a handshake, but it can be a compromised or rented host, and observed infrastructure in general can be borrowed or shared.

A perfect copy of a report's techniques, URLs and hashes, with every callback named in the request, stays `low` (unit and golden tests build both, including a JNDI-style lookup: [`testdata/actors/jndi-callback.input.json`](../testdata/actors/jndi-callback.input.json)). Analysts should treat a match that rests on request content or directed callbacks as a lead, and look for infrastructure the attacker did not choose in front of the decoy, such as where the attack came from or a second hop the implant reached by itself.

## Wording is enforced by code

`statement` is the only sentence UI and exports may show for a link, and only [`actor::statement`](../crates/core/src/actor.rs) writes it:

| Status | Statement |
| --- | --- |
| `pending` | "Possible association with {label}: {TTP, infrastructure, request content, tooling, targeting} overlap with activity reported by {publisher} ({date}) [and N other source(s)]. This is not an attribution." |
| `confirmed` | "Confirmed association with {label}, reviewed by an analyst: {overlap} overlap with activity reported by ..." |
| `rejected` | "An analyst rejected a possible association with {label}." |

`wording` is "possible association" unless an analyst confirmed the link. Report titles are never quoted in text Foiled writes (statements, evidence summaries), because a title may itself make the claim Foiled must not ("... attributed to X"); titles stay as data in `sources[].title`, next to the URL. `actor::wording_problems` refuses attribution phrases ("attributed to", "is behind", "responsible for", "carried out by" and similar) anywhere, and "confirmed" without a confirmation. It runs over curated labels, aliases, publishers and notes (CI), over every ATT&CK group name (unit test), over analyst decision notes (the API refuses a note that claims attribution), and over statements and evidence summaries in the tests. `schemas/actor-link.schema.json` refuses the same phrases, and refuses "confirmed association", `high`, `publishable` or "confirmed" in the statement on a link that is not confirmed.

## Analyst decisions

`POST /v0/actor-links/{link_id}/decision` with `{"decision": "confirm" | "reject" | "reopen", "note": "..."}`:

- `confirm` needs a note saying why. It is the only way to `high`, "confirmed association" and exports. It records the subject's attempts at that moment (`attempt_ids` on the decision) and covers only those: attempts that join the campaign later are listed in `new_since_confirmation`, are not exported as confirmed (they fall back to the unconfirmed link, which never exports), and put the link back in the review queue (`review_queue: true`, and the statement says how many joined since). Confirm again to cover them. Decisions stored before this was recorded cover no attempts.
- `reject` suppresses the link (score 0). It is never suggested or exported again while the decision stands.
- `reopen` returns the link to pending.

Decisions need `review:write`, are rate limited (60 an hour per token), are stored per tenant, subject and actor (latest wins) and apply on every later read, and are written to the audit log as `actor_link.confirm`, `actor_link.reject` or `actor_link.reopen` with the label, the status, score and band before, and the note. MCP tokens cannot hold `review:write`, so an agent cannot confirm an association.

## API and the review queue

| Route | Scope | What it returns |
| --- | --- | --- |
| `GET /v0/actors` | `campaigns:read` | The catalogue, with filters (`q`, `label_kind`, `source`, `technique`), cursor paging and MITRE's notice. |
| `GET /v0/actors/{actor_id}` | `campaigns:read` | One profile. |
| `GET /v0/actor-links` | `campaigns:read` | The tenant's links in the window, strongest first, filtered by `status`, `subject_kind`, `subject_id`, `actor_id`, `review_queue` and `min_confidence`. |
| `GET /v0/actor-links/{link_id}` | `campaigns:read` | One link with its full explanation. |
| `POST /v0/actor-links/{link_id}/decision` | `review:write` | Records a decision and returns the link as it scores now. |

Links are matched on request over the same bounded window as campaigns (default 7 days, at most 20,000 events). `suggested_actor_links[]` (pending and confirmed links, strongest first, at most five, each with `confidence_ref` pointing at `/v0/actor-links/{link_id}`) is filled on campaign detail (`GET /v0/campaigns/{id}`), on the campaign returned by an analyst action, and on the campaign list only with `include=actors`; a plain list does not run the matcher. Store reads for actors (source countries for the explanation, analyst decisions) happen only for campaigns or attempts that matched a profile.

The catalogue is loaded through `actor::CatalogueSource`. The API's source is the bundled ATT&CK groups sidecar plus `catalogue/actors/`; another source (for example a threat intel platform holding actor, intrusion-set and report catalogues) can implement the same trait and goes through the same checks.

The review queue (#35) lists every link that needs analyst attention with `GET /v0/actor-links?review_queue=true`. Do not add `status=pending`: confirmed links whose confirmation does not cover every current attempt need review too. A queue that reads campaigns instead filters `suggested_actor_links` on its own `review_queue` flag (the same rule). Inside the API it can call `routes::actors::actor_model` (filter on `review_queue`) and `routes::actors::record_decision`, which apply the same checks, audit and rate limit as the route.

## Exports

With `include_actors=true`, the STIX and MISP downloads (#13) match actors over the export window and pass the links through `actor::export_links`, which makes one `attempt_actor` link per member attempt and drops pending and rejected links whatever the export options, `include_unreviewed` included. Only confirmed links (the only publishable ones) become a STIX `intrusion-set` with a `related-to` relationship, or a MISP `threat-actor` attribute. The relationship carries the score, `x_foiled_wording` and the export's cautious sentence ("Confirmed association with ..., reviewed by an analyst."). The `intrusion-set` is Foiled's own object: it names the public sources in `external_references` (MITRE's group page with the `G` id for ATT&CK groups, report URLs otherwise) and `x_foiled_actor_id`. An `intrusion-set` derived from an ATT&CK group carries the MITRE ATT&CK notice marking, as the licence register requires, and so does any MISP event holding one. Without `include_actors`, no actor matching runs and nothing about actors leaves.

## Legal and ethical framing

These are design constraints the project follows, not legal advice. Operators should take advice from their own counsel before publishing or acting on any actor association.

- **Assess, do not convict.** Naming an organisation or a person as responsible for unlawful activity can be defamatory if wrong. Foiled names public clusters as their sources describe them, says "possible association", cites the sources, and never says who is responsible.
- **No individuals.** Profiles describe clusters of activity, never people. Do not add personal information about anyone to a profile, a label or a note (Privacy Act 1988 and the APPs; see [privacy-and-retention.md](privacy-and-retention.md)).
- **No active collection or hack-back.** Matching never touches attacker infrastructure. Accessing or interfering with computers without authorisation is an offence under Part 10.7 of the Criminal Code Act 1995 (Cth), whatever the target did ([threat-model.md](threat-model.md)).
- **Respect source terms.** Store facts (ids, indicators, technique ids, dates, URLs) and link to the source, rather than copying report text. Record each publisher's terms in the licence register; ATT&CK content travels with MITRE's notice.
- **Analyst accountability.** Only a person with `review:write` can confirm, every decision is audited with its reason, and a confirmed association still names its sources.
- **Sharing.** Actor links never leave the console unconfirmed. Public pages (#35) and contribute-back ([contribute-back.md](contribute-back.md), #37) follow the same rule.

## What we will not say

- That an actor, country, government, company or person is behind, responsible for or attributed to any activity.
- "Confirmed" about an actor link that no analyst has confirmed, or "attribution" as a claim.
- That geography, a hosting provider or a shared ASN means a shared operator.
- That a technique overlap alone, or a single common technique, links activity to a group.
- That an absence of links means no known actor was involved.
- Anything about an actor that is not in a cited, pinned public source.

## Limits and follow-ups

- **YARA.** Tooling overlap matches SHA-256 values only. YARA rule matches on quarantined payloads ([enrichment.md](enrichment.md)) are not yet compared with report rule names.
- **LLM proposals (#28)** do not produce actor evidence. If they ever do, the caps above still apply.
- **MISP galaxy import.** The source kind and pin fields exist; no galaxy clusters are imported yet.
- **Decisions and merges.** A decision is keyed by campaign id; when a campaign is merged into another, decisions on the merged-away id no longer apply.
- **Window.** Links exist only while their subject is in the read window; decisions persist and apply again when it returns.
